# olcli Workflow

The user wants an ordinary editing request in an associated LaTeX project to include the full Overleaf delivery cycle, without repeating "upload and compile" each time. This is a task workflow; saving a file manually does not launch a background sync.

## Apply the default precisely

- Locate the applicable project root and its `.olcli.json`, including when the edited file is in a subfolder. Resolve the existing `projectId` against the user's account before changing anything. Use the recorded ID, not a potentially ambiguous project name.
- A confirmed association is required. Do not create a project, choose a cloud destination, or bind an arbitrary `.tex` file automatically. Ordinary unlinked LaTeX edits stay local. When Overleaf delivery was requested but the association is missing, invalid, or points to a missing project, ask only for the missing destination information.
- For a substantive editing request, the user's standing preference includes uploading the task's changes and checking an Overleaf build. Proceed within that scope without asking them to repeat this preference. A narrower instruction, such as "local only", takes precedence.
- Questions, explanations, read-only reviews, and requests for suggested changes do not trigger pull/overwrite, upload, or compilation. A request to compile an unchanged project can be handled directly without manufacturing edits.
- Keep existing MCP confirmations and permissions. Never disable olcli's write confirmation or automatically answer an MCP elicitation on the user's behalf.

## Complete the editing task

1. **Inspect and refresh.** Verify the project ID and configured root document through olcli or its MCP tools. Inspect local work, `.olcli.json`, and fresh remote differences before pulling. Preserve pre-existing edits and the pre-pull metadata outside the upload tree. Use a normal `olcli pull` when safe; reconcile existing local work before editing. If local and remote changes overlap, merge only with a known baseline or clear intent; otherwise ask about that conflict. Do not guess that local is authoritative or use `pull --force` as the default.
2. **Edit locally.** Make the requested source, bibliography, and necessary figure changes. Keep unrelated user edits intact and preserve the file's encoding and newline conventions. Use Overleaf's compiler; do not install or invoke a local TeX distribution. Keep transient scripts, build logs, and downloaded output PDFs outside the project upload tree.
3. **Review against the current cloud state.** Run `olcli diff` or the MCP `diff_project` and inspect actual content changes. Distinguish pre-existing differences from this task's edits. If the cloud changed during editing, reconcile before upload; a diff preview does not lock the remote file.
4. **Upload this task's changes.** Proceed without a separate reminder when the requested edit is ready. Use `olcli push` only when its candidate files are all in scope; inspect `push --dry-run` when needed. Otherwise upload the intended files individually, using an explicit project ID and `--to` project-relative path, or MCP `push_file`. Do not upload unrelated pending changes or propagate deletions. Verify the resulting cloud file contents; exit code zero alone is insufficient after a partial upload or uncertain response.
5. **Compile on Overleaf and check the same build's log.** Use the configured root document, or the specific root requested by the user. Prefer MCP `compile_with_outputs`, or the installed olcli library's `compileWithOutputs(projectId, rootPath)`. Fetch the returned build's `output.log` and verify that it produced `output.pdf` and has no LaTeX/fatal errors. Report warnings accurately; producing a PDF or returning `status: success` does not prove a clean build. Do not run another compile merely to retrieve the first build's log. Keep the existing root, compiler, and TeX Live settings unless changing them is part of the task.
6. **Finish the loop.** Correct errors caused by the task, upload those corrections, and recompile. Limit automatic repair to three correction passes and stop sooner if the same failure repeats without progress. Report pre-existing or out-of-scope failures instead of silently changing unrelated work. For appearance-sensitive edits, inspect the actual PDF. Finish with a concise account of the changed files, target Overleaf project, verified upload, compile errors/warnings, and anything unresolved. Clean task-only temporary files after validation.

## Operational details for the installed olcli 0.15.2

- `pull` protects files using modification times, and may skip a file that was already uploaded. It still advances `lastPull`. Inspect skipped files and reconcile their contents before treating the refresh as complete; do not blindly repeat `pull` or let that timestamp erase evidence of pending work. Preserve or restore the pre-pull metadata if a skipped-file conflict remains unresolved.
- `push` also selects files by modification time. `diff` compares content, so use it for the review. Scope an individual upload as `olcli upload <local-file> <project-id> --to <project-relative-path>` when a bulk push would include someone else's edits.
- Use separate pull/review/upload steps for this workflow. `sync` defaults to propagating local deletions and choosing local changes, and `sync --dry-run` can still write local files in this version. Do not use it as a read-only preview. If a separately requested bulk sync is appropriate, disable deletion with `--no-delete` unless the user explicitly asked for the specific deletions.
- A PDF with a same-named `.tex` sibling can be ignored by default. Preserve existing cloud PDFs. Explicitly upload a task-generated PDF figure if it is an actual document input; do not upload a downloaded final build as a source asset or disable all ignore rules indiscriminately.
- The installed MCP exposes `get_project_info`, `pull_project`, `push_file`, `diff_project`, and `compile_with_outputs`. Its `pull_project` extracts files but does not establish CLI `.olcli.json` metadata. Preserve an existing association when using it. CLI and MCP belong to the same installed package; use the appropriate available surface rather than installing another Overleaf integration.
- Resolve the installed package with `npm root -g` when using its public library. It exports `OverleafClient` and `getSessionCookie`; the client's `compileWithOutputs` and `downloadOutputFile` methods support checking one build and its artifacts. Keep session credentials out of prompts, command arguments, and logs. On expired login, permission denial, rate limits, or uncertain writes, stop dependent uploads, preserve local work, and report the needed action; do not retry a write blindly.

The `.olcli.json` project folder can be inside a locally available OneDrive directory. OneDrive replication and Overleaf transfers are separate operations; this skill runs the latter during the Codex task. Git setup, commits, pushes, remote deletion, and sharing changes are outside this default unless requested.
